## 3. Optimisation des appels API

### Cause n°1 : la page Ouvrir lançait 70 requêtes
`site/js/api.js`. Le simulateur d'ouverture (admins) envoie `POST admin-simulate {action:"config"}`.
`config` n'était pas reconnu comme une lecture : le POST était traité comme une écriture, donc `API.invalidate()`
vidait tout le cache **pendant que le lot du gabarit était en vol**. À la fin du lot, `API.batch` relisait
chaque résultat dans le cache (vidé) et relançait les ~45 lectures une par une, puis `loadNavBadges` en
relançait ~25 autres.

Correctifs :
- `API.batch` garde la promesse de chaque lecture et la renvoie directement, au lieu de la relire dans le cache.
- `READ_ACTIONS` côté site inclut aussi les lectures de l'admin : `config`, `stats`, `overrides`, `adminList`,
  `catalog`, `codes`, `redemptions`, `preview`, `tables`, `rows`, `row` (vérifiées côté serveur : aucune n'écrit).
  La route `/batch` du serveur, elle, n'accepte toujours que `status/list/get`.

### Un seul lot par page
- `site/js/shell.js` : `prefetchShellData()` devient `shellReads(withPage)` + `prefetchShellData()`.
  - Lectures de page ajoutées : jeux (pets, fishing, walk, cook), index (server-feed, recent-pulls, leaderboard,
    achievements — l'ancien `API.batch` séparé de `index.html` est supprimé), progression (upgrades),
    trade (wishlist, trade-matches), coffre (showcase), stats (my-stats), pull-log, artistes, salamandre
    (casino `cashier`), profile (fiche publique + sets ; badges et collection sur son propre profil), mode (mode-rules).
  - Lectures communes ajoutées : `secret-card` (si pas en cache d'onglet), `users` (si le pseudo manque),
    `cards`/`extensions` sur les pages qui les lisent (si pas en cache d'onglet).
  - `shellReads(false)` = gabarit seul : utilisé par `loadNavBadges()`, la cloche et le rafraîchissement de 60 s.
- `site/js/core.js` : `Visuals.init()` attend `DOMContentLoaded` pour rejoindre le lot au lieu de partir seul juste avant.
- `api/src/server.js` : `BATCH_MAX` 24 → **64** (tout le gabarit + la page tiennent en un lot).
  `site/js/api.js` : `BATCH_MAX` 64 ; si le serveur n'est pas encore à jour (refus 400 d'un lot > 24), le site
  redescend tout seul à 24 et relance en plusieurs lots.

### Écritures en lot
- `api/src/server.js` : `BATCH_WRITE_PATHS` + `personal-vault`, `wishlist`, `trade`, `showcase`.
- `API.batchWrite` (`site/js/api.js`) : si le serveur refuse un chemin (`invalid_batch`), repli automatique en
  appels individuels, mêmes résultats `{status, json}`.
- Boucles remplacées par un seul `batchWrite` :
  - `site/js/coffre.js` `pvStoreMany` (« Tout ranger »),
  - `site/js/shell-extras.js` `WishlistSync.remove` (souhaits obtenus),
  - `site/js/trade.js` annulation de plusieurs échanges,
  - `site/js/lazy/showcase.js` réordonnancement de la vitrine (retraits puis ajouts, dans l'ordre).

### Correctifs serveur liés
- `/batch` appliquait la réponse brute du handler, **sans `native.scrub`** : le compte test pouvait apparaître
  dans les listes lues en lot (classements, tirages récents…). Le lot applique maintenant le même scrub qu'un appel seul.
- Une lecture qui plantait faisait échouer tout le lot (500), et le site relançait alors chaque lecture une par une.
  Chaque appel du lot a maintenant son `try/catch` (résultat 500 pour lui seul + envoi à GlitchTip).

## 5. GlitchTip

### Site (`site/js/config.js`, `core.js`, `api.js`)
- **`Monitor`** (global, défini dans `config.js`, premier script de chaque page) :
  - `Monitor.capture(err, tags)` ; tant que le SDK n'est pas chargé, les erreurs sont mises en file (30 au plus)
    puis envoyées dès qu'il est prêt ; SDK bloqué (bloqueur de pub) → la file est vidée et la capture coupée.
  - Erreurs non rattrapées et promesses rejetées **avant** le chargement du SDK : capturées (auparavant perdues).
  - `console.error(err)` : une `Error` passée en argument est envoyée.
  - `Monitor.isBug(err)` : vrai pour une erreur de code (TypeError, ReferenceError…) qui n'est ni un refus de
    l'API (`err.code`) ni une coupure réseau.
- `friendlyError(e)` (appelé par presque tous les `catch → Toast.error`) envoie les bugs de code. Les refus
  normaux (pas assez de poussières, déjà récupéré…) ne partent pas.
- `LazyJs.fail(message)` remplace les `.catch(() => Toast.error(...))` des modules chargés à la demande
  (préférences, avis, partage, inspecteur, aide, session rapide, souhaits, notifications) : un module qui plante
  est signalé au lieu d'être avalé.
- `API._report` : toute réponse 5xx (appel seul, lot, appel dans un lot) part avec la route, le statut et le code.

### API
- `api/src/native/index.js` : avis de loterie, scrub du compte test, remise en place des exemplaires assurés.
- `activity.js` (abonnés aux événements), `audit.js` (journal de l'équipe), `starter.js` (date des déblocages).
- `server.js` : chaque appel de `/batch`.
  Tous ces `catch` faisaient seulement `console.error`.

## 11. Fluidité au chargement (Pixel 7 émulé, CPU ÷4)

Profil JS : les plus grosses tâches venaient de **lectures de mise en page forcées** en pleine construction de la page.

| Coupable | Coût mesuré | Correctif |
|---|---|---|
| `spawnFloatingGain` (« +N » de l'en-tête au premier remplissage) | jusqu'à 530 ms | Pas d'animation pendant les 2,5 premières secondes (ce n'est pas un gain), position lue à l'image suivante, plus de reflow forcé (`void offsetWidth`) dans `bumpNumber`. |
| `setCount` (en-tête) | 160 à 640 ms | `window.innerWidth` (force une mise en page) remplacé par `matchMedia` ; `toLocaleString` remplacé par un `Intl.NumberFormat` unique (`fmtNum`). |

| `initHeaderShrink` | 15 à 140 ms | `scrollY` lu au premier défilement. |
| `SecretFx.apply` (cartes secrètes) | 140 à 240 ms (collection) | Deux passes : toutes les lectures, puis toutes les écritures (une mise en page par carte avant). |
| Onglet actif de la collection | ~200 ms | Recentrage à l'image suivante. |

Total des tâches longues sur 10 pages : **6,7 s → 5,5 s** (-18 %). Le JS de l'accueil ne pèse plus que ~60 ms.

## 16. Activités verrouillées par niveau → découvertes

`api/src/native/starter.js` `FEATURE_FINDS` : chaque activité de `StarterUnlocks` s'ouvre par une trouvaille

**filet de sécurité** (« au plus tard »), pour qu'aucun joueur ne reste bloqué. `lockedFor` = niveau pas atteint
**et** pas découvert, donc l'API refuse les écritures (`level_locked`) et le site masque, comme avant.

- Compteurs utilisés : `Users.ActivityCounts` (actions) et `Users.PullStats` (cartes, finitions, raretés),
